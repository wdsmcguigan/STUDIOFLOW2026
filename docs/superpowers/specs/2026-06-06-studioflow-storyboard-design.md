# Storyboard — Visual Development Wedge (Design Spec)

> **Status:** ✅ Finalized 2026-06-06 (resolved in the Storyboard brainstorm).
> **Parent:** `2026-06-02-studioflow-platform-design.md` · **Depends on:** Phases 0–5 (scenes + confirmed breakdown — characters/locations — all exist and are merged to main; hosted Supabase at 0018). New migrations start at **0019**.
> **Research:** technical findings (Gemini API shape, consistency limits, ShotBench taxonomy, prompt templates, open sub-areas) live in the companion `2026-06-06-storyboard-research.md`.
> **Build order:** This is a deliberate **roadmap pivot.** It pulls the spec's Phase 8+ "Storyboard/Previs reading the graph" horizon forward, *ahead of* Phase 6 (granular permissions) and Phase 7 (desktop/mobile). RLS therefore stays **owner-only** for these new tables; membership-awareness lands whenever Phase 6 happens (the longer it waits, the more policies it converts — accepted tradeoff). This is the first slice of a new **Visual Development** workstream (Storyboard → Animatic → Previs; Moodboard's foundation is pulled into this slice as Visual References).

## Goal

The first creative/generative module: an **AI-drafted, reference-consistent storyboard anchored to the production graph.** Open a Scene → **"Board this scene"** → an async job has the AI **decompose the scene into a shot list** *and* **render a consistent panel per shot** → the human curates (reorder, pick a variant, regenerate, upload their own art, confirm/reject) → **export a storyboard PDF**.

It is the sixth proof of the thesis, but the **first module that is primarily a graph *consumer*** (downstream of script + breakdown): a panel's prompt is auto-assembled from the scene's INT/EXT, D/N, location, characters-present, synopsis and action — so *change the breakdown → re-boarding reflects it*, and renumbering a scene never detaches its board (panels key to the immutable `scene_id`/`shot_id`, never to display numbers — non-negotiable #5). Consistency across panels is achieved by **conditioning generation on locked reference images** of the Characters present and the scene's Location — which doubles as the **Moodboard foundation**.

This is **not** a Midjourney wrapper. The differentiator — the whole reason it belongs in StudioFlow — is that it reads the one shared model and stays consistent because of it. We build the focused, genuinely-useful generative storyboard and hold the line against: real (3D) previs, animatic timing/audio, full moodboard collages/palette extraction, LoRA/ControlNet composition control, and collaboration — all deferred seams.

## Decisions (resolved 2026-06-06)

| # | Decision | Choice | Rationale |
|---|---|---|---|
| 1 | **Wedge** | **Storyboard first** (of Moodboard / Storyboard / Animatic / Previs) | Strongest graph fit (panel→scene), highest pre-pro value, and the unit the others build on (an animatic *is* a timed storyboard; a previs shot is a richer panel). The other three are sequenced behind it. |
| 2 | **Core unit** | **Shot-first — shots are first-class graph entities** | A `shots` table (immutable `shot_id`, scene-anchored, reorderable ordinal, size/angle/movement/lens/action). Image **frames** attach to shots. Shots become reusable graph citizens — a future shot-list view and a *shots → schedule timing* feed are then additive seams, not a refactor. Honors immutable-identity properly. (User chose this over panel-only / hybrid.) |
| 3 | **AI authorship** | **Full first-draft — decompose *and* render** | "Board scene" produces a **suggested shot list** (structured output) *and* a rendered panel per shot, all non-destructive `suggested` results a human confirms — the Phase-2 breakdown pattern applied to coverage. Per-shot manual generate + manual "add shot" also exist. (User chose this over render-only / fast-follow.) |
| 4 | **Visual consistency** | **Reference-conditioned (pull the mini-Moodboard in)** | A first-class **`visual_references`** concept: a lockable reference image per **Character** (a "character sheet") and per **Location** (a "plate"), AI-generated-and-locked or uploaded. Panel generation conditions on the locked refs for **characters-present + the scene's location** → genuinely consistent panels. This *is* the Moodboard foundation, so full Moodboard later is additive. (User chose this over style-only / characters-only / seam-only.) |
| 5 | **Image provider** | **Provider-agnostic engine; Gemini Flash Image default; marketplace adapter as seam** | A swappable `ImageEngine` interface mirroring the Phase-2 text engine. Default adapter = **Gemini Flash Image** (the "Nano Banana" line) for its **native multi-image reference conditioning** (consistency works without us building an IP-Adapter pipeline), routed via the Vercel **AI Gateway** as a `provider/model` string (non-negotiable #3). A **Replicate/fal** adapter (Flux + IP-Adapter / ControlNet / LoRA) is a documented seam for later compositional control. Exact model id confirmed against current docs (context7) at plan time. |
| 6 | **Cost control** | **Counter + confirm-on-batch** | An append-only **`image_generations`** ledger (mirrors `cost_entries`) records every generation (model, image count, est. cost). A **confirm dialog** precedes any batch over a threshold ("this will generate 12 images, ~$X — proceed?"). A running counter chip shows project image spend. **No hard cap / no BYO-key** in v1 (both seams). Generation already runs as cancellable, concurrency-bounded jobs. |
| 7 | **Re-board on revision** | **Non-destructive *append*; smart diff is a seam** | Re-boarding an already-boarded scene **adds new `suggested` shots and never deletes/overwrites confirmed shots or selected frames**. Full stage→diff→apply reconciliation (match/update/retire like the import adapter) is a designed seam, not built now — the v1 guarantee is simply "your confirmed work survives a re-board." |
| 8 | **Frame model** | **One `is_selected` frame per shot; variants retained; motion = seam** | A shot has many `shot_frames`; exactly one is `is_selected` (the panel shown/exported); the rest are retained alternates (non-destructive, mirrors breakdown suggestions). Multi-frame *motion sequences* within a shot (start→end) are a seam — a `frame ordinal` column exists but v1 treats frames as variants of a single panel. |
| 9 | **Storage** | **Private `storyboards` bucket, project-namespaced, signed URLs** | Supabase Storage; object paths prefixed by `project_id`; RLS on `storage.objects` gates by owner (same predicate as the tables); the app serves images via short-lived **signed URLs**. The `service_role` key never reaches the browser (non-negotiable #1). |

> **Soft-modeling guards (additive seams, ~free now):** (i) **shots → schedule** — shots exist as real entities, so a later "shots-per-scene → day timing estimate" feed is additive, no schema change to schedule; (ii) **full Moodboard** — `visual_references` is the seed; mood collages / palette extraction / project boards hang off it; (iii) **Animatic** — `shots` ordered per scene + `shot_frames` are exactly what an animatic sequences; a later `animatics`/per-shot-duration table is additive; (iv) **provider power** — the `ImageEngine` interface means a Replicate/fal adapter (LoRA/ControlNet) is config+code behind the same seam, no schema change; (v) **collaboration** — owner-only RLS today; Phase 6 swaps the one predicate (ideally via an `is_project_member` helper) across these tables alongside the rest.

## Data model (additions to the graph)

All new tables are **project-scoped** with **owner-based RLS** (the Phase 1–5 pattern), per-op policies, `text + CHECK` "enums", FK indexes, `updated_at` triggers. Tables with **two cross-entity FKs validate both** in insert/update `with check` via `SECURITY DEFINER` same-project helpers (`set search_path = ''`, `stable` — the 0013 `..._owned_by` pattern). Forward-only migrations continue from **0019**. Regenerate `lib/db/types.ts` after each migration (`npx supabase gen types typescript --local 2>/dev/null > lib/db/types.ts`; verify line 1 is `export type Json =`).

### Migration 0019 — Storage bucket + visual settings + references (the Moodboard seed)
- **Storage:** create a **private** bucket `storyboards`. Policies on `storage.objects` for `bucket_id = 'storyboards'`: select/insert/update/delete allowed when `((storage.foldername(name))[1])::uuid` is a project the caller owns (`exists (select 1 from public.projects p where p.id = ... and p.owner_id = auth.uid())`). Paths: `<project_id>/references/<reference_id>.<ext>` and `<project_id>/shots/<shot_id>/<frame_id>.<ext>`.
- **`project_visual_settings`** — one row per project (lazy get-or-create, the 0016 "one-default" pattern; `project_id` UNIQUE): `{ id, project_id (FK projects, cascade) UNIQUE, style_preset text not null default 'storyboard_sketch' CHECK in (a small named set), custom_style_prompt text?, aspect_ratio text not null default '16:9' CHECK in ('16:9','2.39:1','4:3','1:1'), created_at, updated_at }`. The style + aspect feed every prompt.
- **`visual_references`** — `{ id, project_id (FK projects, cascade), subject_type text not null CHECK in ('character','location'), character_id uuid? (FK characters, cascade), location_id uuid? (FK locations, cascade), image_path text?, source text not null default 'ai' CHECK in ('ai','upload'), status text not null default 'suggested' CHECK in ('suggested','locked','rejected'), is_primary boolean not null default false, prompt_used text?, generation_metadata jsonb, created_by uuid? (FK auth.users), created_at, updated_at }`. **CHECK** exactly one of `character_id`/`location_id` is set and matches `subject_type`. **Two-FK with-check:** project + the set subject FK both owned. **Partial unique** `(character_id) where is_primary` and `(location_id) where is_primary` — at most one primary/locked reference per subject (the one conditioning conditions on). Generation produces variants (`suggested`); the human **locks** one → `status='locked', is_primary=true`.

### Migration 0020 — Shots + frames (storyboard core)
- **`shots`** — `{ id (the immutable shot_id), project_id (FK projects, cascade), scene_id uuid not null (FK scenes, cascade), ordinal int not null, shot_number text?, (mutable display, e.g. "1A"), size text? CHECK in ('EWS','WS','MS','MCU','CU','ECU','INSERT','POV','OTS','2SHOT'…), angle text?, movement text? CHECK in ('STATIC','PAN','TILT','DOLLY','TRACK','CRANE','HANDHELD','ZOOM'…), lens text?, action text?, status text not null default 'suggested' CHECK in ('suggested','confirmed','rejected'), provenance text not null default 'ai' CHECK in ('ai','manual'), text_anchor jsonb? (seam: script range that produced it, mirrors scene_elements), created_by uuid?, created_at, updated_at }`. Scoped via `scene_id → scenes.project_id` **and** carries `project_id` (denormalized like other tables for simple RLS). **Two-FK with-check:** project + scene both owned. Index `(scene_id, ordinal)`.
- **`shot_frames`** — `{ id (frame_id), project_id (FK projects, cascade), shot_id uuid not null (FK shots, cascade), image_path text not null, source text not null default 'ai' CHECK in ('ai','upload'), status text not null default 'suggested' CHECK in ('suggested','selected','rejected'), is_selected boolean not null default false, ordinal int not null default 0 (motion seam), prompt_used text?, generation_metadata jsonb (model, refs_used:[reference_id], seed, params), created_by uuid?, created_at, updated_at }`. Scoped via `shot_id → shots.project_id`; **two-FK with-check** (project + shot owned). **Partial unique** `(shot_id) where is_selected` — at most one selected frame per shot. Index `(shot_id, ordinal)`.

### Migration 0021 — Generation cost ledger
- **`image_generations`** — append-only (mirrors `cost_entries`; no UPDATE/DELETE policy): `{ id, project_id (FK projects, cascade), job_id uuid? (FK jobs), kind text not null CHECK in ('decompose','render','reference'), model text not null, image_count int not null default 0, est_cost numeric not null default 0, created_by uuid?, created_at }`. Index `(project_id, created_at)`. The counter = `sum(est_cost)` / `sum(image_count)` per project.

> **Jobs:** **no new table** — reuse the Phase-2 `jobs` table; add `type` values `storyboard_decompose`, `storyboard_render`, `reference_generate` (the column is free-text). Jobs run via the existing managed runner (WDK, service-role background, the Phase-2 mechanism), cancellable, bounded concurrency (respects provider rate limits).

## Generative engine (`lib/ai/image/*` — swappable; the generative core)

Mirrors the Phase-2 text engine abstraction. Pure-ish: the engine does I/O (provider call) but is injected, so the data layer is tested against a **fake engine** (no live API, no key, deterministic).

> **🔴 API shape (corrected by the [research companion](2026-06-06-storyboard-research.md)):** Gemini Flash Image is a **multimodal LLM** — it is called via **`generateText`**, *not* `generateImage`/`experimental_generateImage`. References pass as `image` content parts in the `messages` array; generated images come back in **`result.files`**. Image-*only* providers (Imagen/Flux/gpt-image) use the *other* shape (`experimental_generateImage` → `result.images[].base64`). So the `ImageEngine` interface **abstracts over two return shapes** — that's the whole point of the seam.

- **`ImageEngine` interface** — `generate({ prompt, references: RefImage[], aspectRatio, n }) → { images: Bytes[], meta }`. Adapters normalize each provider's native call/return into this one shape. `references` are the locked character/location plates passed as conditioning inputs.
- **`GeminiImageEngine`** (default) — calls **`generateText({ model: <configured id>, messages: [{ role:'user', content: [ {type:'text', text: prompt}, ...references.map(r => ({type:'image', image: new URL(r.signedUrl), mediaType: r.mediaType})) ] }] })`** via the AI Gateway (bare `provider/model` string, `ai` ≥ v5.0.36, no wrapper) → reads images from `result.files`. Native multi-image fusion = consistency without an IP-Adapter pipeline. **Model id is config-driven** (env/setting), current default `google/gemini-2.5-flash-image`; newer same-call-shape variants exist (`gemini-3.1-flash-image-preview`, `gemini-3-pro-image`) — **verify the current id + `ai` version at plan time** (the research flagged these as post-cutoff/time-sensitive).
- **Independent per-panel generation (load-bearing):** each panel is generated **fresh from the locked plates** — *never* chained as one long iterative-edit conversation (Google's own docs warn identity drifts over edit chains). This is *why* human re-roll/curation is first-class; consistency is best-in-class but **not pixel-perfect** — the plan must not promise pixel-perfect locking.
- **Ref budget:** condition on the **principal characters present + the scene's location plate**, capped at **~3–6 references** (fidelity degrades beyond ~6) — `selectConditioningRefs` enforces the cap (principals first).
- **`ReplicateImageEngine`** (seam, not built) — image-only shape (`experimental_generateImage`); Flux+IP-Adapter/ControlNet for later compositional control.
- **`FakeImageEngine`** (tests) — returns a deterministic 1×1 PNG + echoes the prompt/refs in meta so prompt-assembly and ref-selection are assertable (no key, no network).
- **Decompose** reuses the **Phase-2 text engine** with **structured output** (Zod schema for the shot list) — not the image engine.

### Flows
- **`boardScene(sceneId)`** → `storyboard_decompose` job → text engine returns a Zod-validated **shot list** (size/angle/action per shot, derived from the scene slice) → insert `shots` as `suggested` (ordinals sequential) → enqueue one **`storyboard_render`** job per shot. *Before enqueue*, the count is known → **confirm-on-batch** dialog → on confirm, append `image_generations(kind='decompose')` and the render jobs run.
- **`renderShot(shotId)`** (one `storyboard_render`) → assemble the **prompt** from: scene context (INT/EXT, D/N, location name, synopsis, action) + shot fields (size/angle/movement/lens) + **project style + aspect** + the shot's `action` → gather **conditioning refs**: locked `visual_references` for the **characters present in the scene** (`scene_characters → characters`) + the **scene's location** plate → call `ImageEngine.generate` → store image(s) in the `storyboards` bucket → insert `shot_frames` as `suggested` (first becomes `is_selected` if none yet) → append `image_generations(kind='render')`.
- **`generateReference(subjectType, subjectId)`** → `reference_generate` job → prompt from the character's/location's graph attributes + project style → N variants stored + `visual_references` rows `suggested` → human **locks** one (`lockReference`) → it becomes the conditioning ref.
- **Non-destructive everywhere:** regenerate **adds** frames/variants (never overwrites); re-board **appends** suggested shots and leaves confirmed shots/selected frames untouched (Decision #7). Cancellation is always safe (results are suggestions).

## Services & layout

- `lib/storyboard/schema.ts` — Zod rows + write inputs + the **shot-list structured-output schema** + derived/result types (`ShotWithFrames`, `SceneBoard`, `ReferenceState`).
- `lib/storyboard/data.ts` — the only place storyboard queries live: CRUD for `shots`, `shot_frames`, `visual_references`, `project_visual_settings` (`getOrCreateVisualSettings`); `getSceneBoard(sceneId)` (shots + selected frame + signed URLs, parse-on-read); reorder/select/confirm/reject; a **graph-slice loader** that **reuses `lib/breakdown`** (scene + characters-present + location) and assembles render prompts; never re-queries breakdown ad hoc.
- `lib/storyboard/prompt.ts` — **pure** prompt assembly (scene slice + shot + style → prompt string; + ref selection) → unit-testable with no I/O. Uses **Google's verbatim comic-panel template** ("A single comic book panel in a *[art style]* style. In the foreground, *[character + action]*. In the background, *[setting]*. … *[mood]* mood. *[aspect ratio]*."), folding the shot's size/angle/movement/action into the foreground/composition slots and `[art style]`/`[aspect ratio]` from `project_visual_settings`. Pure helpers also: `selectConditioningRefs(sceneSlice, lockedRefs)` (principals + location, capped ~3–6). The shot-list structured-output enums derive from the **ShotBench** taxonomy (see research companion). Both templates cited in [2026-06-06-storyboard-research.md](2026-06-06-storyboard-research.md).
- `lib/storyboard/jobs.ts` — the decompose/render/reference job handlers (call the engine, write rows, append the ledger). Reuse the Phase-2 job runner + service-role client.
- `lib/ai/image/*` — the engine interface + Gemini adapter + fake (above).
- `lib/storage/storyboards.ts` — upload + signed-URL helpers for the `storyboards` bucket (server-only; service-role never sent to client).
- `app/dashboard/[projectId]/storyboard/{page.tsx,actions.ts}` + a per-scene view — actions **Zod-parsed**, `"use server"` hygiene (**only locally-defined async exports** — the manifest footgun): board-scene, render-shot, regenerate, select-frame, confirm/reject-shot, reorder, add-manual-shot, upload-frame, set-style, generate/lock-reference.
- `components/storyboard/*` — scene picker, the per-scene **board** (ordered grid of shot panels: selected frame + metadata + status badge), **dnd-kit** reorder, per-shot actions (variant picker, regenerate-with-edited-prompt, upload, edit metadata, confirm/reject), the **Visual References** surface (characters & locations with their locked ref + generate/upload/lock), style settings, the **cost counter chip**, the **confirm-on-batch** dialog, **Export-PDF** button. Ported onto the design system; **design tokens only** (sage→amethyst for AI surfaces, per the design foundation).
- `lib/storyboard/pdf/storyboard-document.tsx` + `app/dashboard/[projectId]/storyboard/[sceneId]/pdf/route.ts` — `@react-pdf/renderer` (Phase-5 infra) → classic panels-with-metadata layout; streams the selected frames in shot order. (Frames fetched server-side via signed URL / service-role read.)
- **Async generation** via the existing job queue/panel; **PDF** synchronous on request.

## Key flows

Open the **Storyboard** module → pick a Scene (scenes from the script). If the scene has no shots, **"Board this scene"** → confirm-on-batch (count + est. cost) → the AI proposes a shot list and renders a consistent panel per shot (job-queue panel shows progress; cancellable). The board renders as an ordered grid of shot panels with size/angle/action and a `suggested` badge. The human **reorders** (dnd-kit), **picks variants** / **regenerates** a panel, **uploads** their own art, **edits** shot metadata, **confirms/rejects** shots, or **adds a manual shot**. To make characters/locations consistent first, open **Visual References**, generate or upload a reference for each Character/Location and **lock** it — subsequent renders condition on the locked refs. Set the project **style preset + aspect**. **Export PDF** → a storyboard document of the selected frames in order. Change the breakdown (a character's presence, the scene's location, the synopsis) → re-boarding (or regenerating a shot) reflects it with no re-keying; renumbering the scene never detaches its board.

## Testing

- **Pure unit (prompt + ref selection):** `assemblePrompt(sceneSlice, shot, style)` includes INT/EXT, D/N, location, action, style, aspect; `selectConditioningRefs` returns the locked refs for exactly the characters present + the scene's location (and none for absent characters / unlocked refs). Deterministic, no I/O.
- **Engine-injected data-layer tests (FakeImageEngine, no key):** `boardScene` inserts a valid suggested shot list + enqueues N renders; `renderShot` stores a frame `suggested`, sets `is_selected` only when first, passes the right refs to the engine (assert via fake's echoed meta); regenerate **adds** a variant (count grows, prior `is_selected` unchanged); `selectFrame` flips exactly one `is_selected` (partial-unique honored); re-board **appends** and leaves confirmed shots/selected frames intact (Decision #7); `image_generations` rows appended per generation.
- **⭐ Cross-module integration test (the thesis):** seed a project + script + scene with **confirmed** characters-present + a location. `boardScene` → shots created; assert the assembled render prompts reference the seeded characters + location. Then **reject a character's presence** → re-board's prompt drops that character. **Change the location** → prompt reflects the new plate/location. **Renumber the scene** (`scene_number`) → the board's shots stay attached (keyed to `scene_id`). Proves the storyboard *consumes* breakdown live.
- **RLS:** two-user isolation on `shots`, `shot_frames`, `visual_references`, `project_visual_settings`, `image_generations`; **two-FK escapes** (shot→scene cross-project, frame→shot, reference→character/location); **Storage** isolation (a non-owner cannot read another project's `storyboards` objects / signed URLs); `describe.skipIf(!SUPABASE_SERVICE_ROLE_KEY)`.
- **PDF:** `renderToBuffer` of the `<Document>` for a seeded `SceneBoard` produces a non-empty `%PDF` (no snapshot brittleness).
- **Live-image precision** (manual, skipped without an API key — mirrors the Phase-2 live-AI deferral): one real generation; eyeball character consistency across two panels of the same scene.
- **Component/browser smoke** (dev server via Bash + Chrome extension + Mailpit OTP/PKCE — the preview MCP can't run a dev server on the external volume): sign in → open a project with breakdown → Storyboard → lock a character reference → Board a scene (confirm-on-batch) → see panels render in the job panel → reorder + select a variant + confirm a shot → Export PDF (route returns `%PDF`) → confirm a `"use server"` action POSTs 200 (no manifest 404).
